# BOMwitness

BOMwitness checks a declared bill of materials for an IoT firmware image (SBOM, CBOM, and a presence check
for AI-BOM) against the bytes of the image. It does not trust the package database that ships inside the
firmware.

Built for the SafeIoT Hackathon 2026, Track 2 (IoT SBOM, CBOM and AI-BOM verification).

## Why

Open-source SBOM tools for Linux firmware take their inventory from the device's own package database
(`/usr/lib/opkg/status` on OpenWrt). A verifier built on that inventory can tell you whether the BOM agrees
with what the firmware says about itself. When the database is stale, was generated by the same faulty
process as the BOM, was edited, or was stripped to save flash space (common in vendor firmware), there is
nothing left to check against. A binary that was swapped or patched under an unchanged label is invisible
in every case.

BOMwitness compares each claim with the publisher's signed release material instead and grades the evidence:

| Grade | Evidence | Used for verdicts |
|---|---|---|
| A | A file is byte-identical to the file in the publisher's package (usign-signed index, then per-file SHA-256). The version label comes from the feed index, the signed release manifest, or an official sibling image of the same release. | yes |
| B | Intrinsic to the bytes: the version marker that the reference build of the component carries, SONAMEs, algorithm names | yes, labelled B |
| C | The firmware's own package database | no. Shown in its own section, labelled self-reported |

Per declared component the result is `verified_A`, `verified_B`, `wrong_version`, `wrong_component`,
`absent`, `bytes_differ` (needs review), `label_unconfirmed` (needs review) or `unverifiable`. Per image it
reports `undeclared_component` and `undeclared_file`. The CBOM check covers certificates, keys and algorithm
names, and requires every declared algorithm to be provided by an SBOM component whose bytes verified.
The rules are in [docs/DESIGN.md](docs/DESIGN.md).

## Quick start

```sh
python -m venv .venv && .venv/bin/pip install -e ".[test]"
.venv/bin/pytest -q                                   # 80 offline tests on a synthetic signed feed
sh pipeline/pipeline_harness/bomwitness/run.sh        # end to end on one official image, ends with PASS
```

Verify your own declaration:

```sh
bomwitness verify --image firmware.bin --sbom declared.cdx.json \
    --release 24.10.8 --target ath79/generic --sibling-image official-sibling.bin \
    --json report.json --md report.md
```

Input: CycloneDX 1.4 to 1.6 JSON or SPDX 2.3 JSON. Output: a JSON report, a Markdown report and exit status 1
when there are findings. `bomwitness inventory` derives a component list from the bytes alone, for an image
that comes with no BOM and no database. An example report is in
[pipeline/4_analysis_output/bomwitness/](pipeline/4_analysis_output/bomwitness/).

Nothing from the firmware is executed. OpenWrt images and packages are downloaded from
downloads.openwrt.org, checked against pinned usign keys, and never redistributed here.

### How to read this

- **The comparison that matters is across the database rows.** BomTrace and the Syft-based diff find every
  BOM-level error when the database is honest, and none when it agrees with the wrong BOM or is missing.
  That is what their own documentation says would happen. BOMwitness gives the same answer in all three
  rows because it never reads the database. The tools are complementary: with an honest database, reading
  it finds the few label errors that bytes cannot refute.
- **High recall here follows from the design, not from cleverness.** Comparing hashes against a signed
  reference finds a flipped byte every time. The informative numbers are the false alarms on clean images,
  the misses, the ablations and the drift measurement.
- **These are official images checked against their own publisher's packages**, the case where byte
  identity is available. Firmware that a vendor rebuilds from source will not match byte for byte; the
  downstream-fork case study shows what is left then.
- **The sibling snapshot is close to a copy of the tested image for most benchmark devices**, because
  devices of one OpenWrt target share nearly all packages. It is always a different official file, and in
  an audit of vendor firmware it is the right reference, but for this benchmark the "no sibling snapshot"
  column is the conservative one.
- **Seeded errors are not field data.** See [docs/LIMITATIONS.md](docs/LIMITATIONS.md).

## How it relates to other tools

- **BomTrace** (`ssophiz/bomtrace-iot-bom-verifier`, also written for this hackathon) reconciles OpenWrt's
  published BOMs with the opkg or apk database and is careful about its scope: its README states that the
  database is not independently authenticated and that a one-byte change to BusyBox produces no finding.
  BOMwitness starts from that gap. BomTrace also supports apk-based 25.12 images and a hash-carrying BOM
  profile, which BOMwitness does not.
- **Syft** and **cve-bin-tool** are generators and scanners, not verifiers. They appear as baselines only
  through small diff scripts of ours (`bench/baselines.py`).
- **JBomAudit** (NDSS 2025), the example tool in the SafeIoT supply-chain pipeline, checks Java SBOMs
  against JAR contents. BOMwitness applies the same idea, verify the BOM against the artifact and not
  against metadata, to firmware.
- Commercial binary analysis products advertise SBOM validation against firmware. They are closed, so
  nothing here is compared with them.

## Scope

In: OpenWrt opkg releases (tested on 23.05 and 24.10, seven package architectures), SBOM and CBOM
verification, cross-BOM consistency, a model-file presence check. Out: executing firmware, encrypted
images, apk-based releases, vulnerability matching, and any claim about firmware families that were not
measured. The AI-BOM part is a presence check exercised only by synthetic unit-test fixtures, because the
evaluated router images contain no models.
