# BOMwitness

BOMwitness checks a declared bill of materials for an IoT firmware image (SBOM, CBOM, and a presence check
for AI-BOM) against the bytes of the image. Its verdicts do not use the package database that ships inside the
firmware; that database is shown in a separate, labelled section of the report.

Built for the SafeIoT Hackathon 2026, Track 2 (IoT SBOM, CBOM and AI-BOM verification).

- Paper: [paper/bomwitness.pdf](paper/bomwitness.pdf). Every number in it is generated from the result files
  in this repository and checked against the PDF by a script ([paper/README.md](paper/README.md)).
- Pitch video (under 5 minutes, captions, synthetic narration): link in the hackathon submission.
- License: MIT. Built with AI coding agents under the author's direction; see
  [AI assistance](#ai-assistance-provenance-and-license).

  scored. This repository carries the development history, so `git diff rules-frozen-r2a -- bomwitness bench`
  shows everything that changed afterwards.

## Why

The open tools evaluated here (BomTrace's database mode and a diff built on Syft's inventory) take their
package inventory from the device's own package database (`/usr/lib/opkg/status` on OpenWrt). A verifier
built on that inventory can tell you whether the BOM agrees with what the firmware says about itself. When
the database is stale, was generated by the same faulty process as the BOM, was edited, or was removed
(OpenWrt's build system has an option for that; how often vendors use it was not measured), there is nothing
independent left to check against. A binary that was swapped or patched under an unchanged label is
invisible to that comparison in every case.

BOMwitness compares each SBOM claim with the publisher's release packages instead and grades the evidence.
The packages are authenticated through a chain: one usign signature on the target's checksum file, checked
against pinned keys, pins the per-target package indexes, the image list and the release manifest by hash;
shared feed indexes carry their own signatures; each package is checked against its index hash; files are
compared by SHA-256. Files are hash-pinned through that chain. They are not signed one by one.

| Grade | Evidence | Used for verdicts |
|---|---|---|
| A | No compared file of the package differs from the publisher's package. The package's files that are present in the image are compared by SHA-256, with three stated limits: configuration files and three account files count as matches when they are identical and are skipped when they differ; a file that differs only inside embedded build-date strings is accepted (those strings are masked before comparison); and the package need not be complete. A grade A pass can therefore rest on few matched files, in the extreme on none, and the report line then says that no file was positively matched. Each grade A line of a report gives the counts. The version label comes from the feed index, the hash-pinned release manifest, or a sibling image of the same release. | yes |
| B | Intrinsic to the bytes: the version marker that the reference build of the component carries, SONAMEs, algorithm names | yes, labelled B |
| C | The firmware's own package database | no. Shown in its own section, labelled self-reported |

Per declared component the result is `verified_A`, `verified_B`, `wrong_version`, `wrong_component`,
`absent`, `bytes_differ` (needs review), `label_unconfirmed` (needs review) or `unverifiable`. Per image it
reports `undeclared_component` and `undeclared_file`.

Only SBOM claims are compared with the authenticated reference. The CBOM check compares the certificates,
keys and algorithm names found in the image with the declaration, and no signed reference is involved in
that comparison: certificates are matched by fingerprint (by subject when the declaration gives no
fingerprint and the subject is unique in the image) and then compared field by field, standalone keys are
reconciled by fingerprint only. One CBOM rule reaches the reference indirectly: every declared algorithm
must name a providing SBOM component, and that component's SBOM check must have ended in a grade A or B
pass. The AI-BOM check compares the hashes of the model files found in the image with the declaration and
uses no reference at all. The rules are in [docs/DESIGN.md](docs/DESIGN.md).

A sibling image is one more input, and the report keeps apart what was authenticated and what was only
supplied. A sibling whose SHA-256 is in the release's image list is called authenticated. A sibling that is
not listed, or a local snapshot file, still supports verdicts, on your trust in it. Every verdict and
finding that rests on a sibling, a snapshot file or another release (`--alt-release`) names that input,
says whether it was authenticated, and gives the version that input records, in its text and in an
`evidence` field of the JSON report. A file that only a snapshot matched is reported with the snapshot's
version of the package, not with the label the feed carries today. No finding calls an unauthenticated
source official.

Grade A is the tool's verdict under those rules. It is not a proof of a positive match or that a package is
complete: three phantom packages in the held-out benchmark were accepted because one of their files was
present with the right bytes ([docs/LIMITATIONS.md](docs/LIMITATIONS.md), item 8), and a package whose only
file in the image is a changed configuration file passes with zero matched files. When a file differs from
the primary release's reference, one file that matches another release's build of the declared version is
enough for grade A; the reason gives the counts, including files that match neither build.

## Quick start

```sh
python -m venv .venv && .venv/bin/pip install -e ".[test]"
.venv/bin/pytest -q                                   # offline unit tests on a synthetic signed feed
sh pipeline/pipeline_harness/bomwitness/run.sh        # end to end on one official image, ends with PASS
sh examples/aibom/unified.sh                          # SBOM, CBOM and AI-BOM in one run (synthetic models), ends with PASS
```

Needs Python 3.10 or newer, `curl` and about 25 MB of downloads for the second command (one official OpenWrt
image, its sibling and the reference packages it touches). The harness takes under a minute. It calls
`bomwitness verify` with `--fail-on never`, compares the SBOM and CBOM findings of the run with the expected
ones in `pipeline/1_analysis_object/bomwitness/expected-findings.json`, and exits 0 when they match, so it
ends in PASS with the seeded failing findings present. It does not run the AI-BOM example. The third
command adds two placeholder model files to the same root filesystem and checks all three BOM types in one
`bomwitness verify` call; the subject is synthetic and the report title says so.

Verify your own declaration:

```sh
bomwitness verify --image firmware.bin --sbom declared.cdx.json \
    --release 24.10.8 --target ath79/generic --sibling-image official-sibling.bin \
    --json report.json --md report.md
```

Input: CycloneDX 1.4 to 1.6 JSON or SPDX 2.3 JSON. The reader takes the fields the checks use (names,
versions, hashes of model components, cryptographic assets); it does not validate a document against either
schema or against SBOM minimum elements. Output: a JSON report and a Markdown report.

Exit status is 1 when there is an SBOM finding of class `wrong_version`, `wrong_component`, `absent`,
`bytes_differ`, `undeclared_component` or `undeclared_file`, a CBOM finding other than a
deprecated-algorithm observation, or an AI-BOM finding. `label_unconfirmed`, `unverifiable` components and
disagreements with the device database do not change it. `--fail-on never` always exits 0.

What you must trust, and what the tool checks for you:

- **Release metadata and packages** are fetched from `downloads.openwrt.org` (or `--base`) and authenticated
  with the pinned keys. Nothing to do.
- **`--sibling-image`** is an input you supply. The tool looks its SHA-256 up in `profiles.json` (the image
  list of the release and target). That file carries no signature of its own: the signed `sha256sums` pins
  it by hash. The first lines of the command's output, and the report, say whether the image was found. An
  image that is not listed is still used, with a warning, and findings that rest on it call it a supplied
  sibling image that was not authenticated. Use an official image of the same release and target.
- **`--snapshot`** (a JSON file made by `bomwitness snapshot`) is a local file and is trusted as supplied,
  whatever it says about its own origin. The output says so, and findings that rest on it say "the supplied
  snapshot (not authenticated by this run)", followed by the file's name in square brackets.
- **`--alt-release`** names another release of the same target whose builds may be compared. Its reference
  is fetched and authenticated like the primary one, and the first lines of the output name the key that
  signed its checksum file.
- **The cache directory** (`--cache`) is verified when an item is first fetched and trusted afterwards. Keep
  it where only you can write, or delete it to force a fresh, verified download.

`bomwitness inventory` derives a component list from the bytes alone, for an image
that comes with no BOM and no database. An example report is in
[pipeline/4_analysis_output/bomwitness/](pipeline/4_analysis_output/bomwitness/). Example BOM artifacts: SBOM and
CBOM in [pipeline/1_analysis_object/bomwitness/](pipeline/1_analysis_object/bomwitness/), AI-BOM (synthetic) in
[examples/aibom/](examples/aibom/).

Nothing from the firmware is executed. OpenWrt images and packages are downloaded from
downloads.openwrt.org, checked against pinned usign keys, and never redistributed here.

### How to read this

- **The comparison that matters is across the database rows.** BomTrace and the Syft-based diff find every
  BOM-level error when the database is honest and none when it agrees with the wrong BOM. When the database
  is missing, BomTrace's verifier has no usable input and returns no result (unsupported input, which is
  not the same as finding nothing), and the Syft-based diff reports every declared component as absent,
  which credits it with the 120 phantom rows and nothing else. That is what their own documentation says
  would happen. BOMwitness gives the same answer in all three rows because its verdicts never read the
  database. The tools are complementary: with an honest database, reading it finds the few label errors
  that bytes cannot refute.
- **This is not a ranking of firmware tools.** Two of the three baselines are small adapters of ours around
  a generator and a scanner, the Syft adapter's naming differences cost it precision that Syft itself does
  not deserve, and no firmware-native analyser such as EMBA was run.
- **High recall here follows from the design, not from cleverness.** Comparing hashes against an
  authenticated reference finds a flipped byte only where a comparable reference covers the file: all 120
  one-byte patches of the held-out set with the sibling snapshot, 116 of 120 without it (the four misses
  are in packages whose shared-feed copy has moved to a newer version). A change inside a masked build-date
  string, or in a configuration file that is not compared, would not be reported. The informative numbers
  are the false alarms on clean images, the misses, the ablations and the drift measurement.
- **900 distinct errors, not 1860 independent cases.** Each BOM-level error is scored under three database
  states. Errors on one image share its packages and reference, so the per-image range of recall is a better
  guide to variability than a pooled interval. Seeded targets are drawn from packages the reference covers.
- **These are official images checked against their own publisher's packages**, the case where a grade A
  match is available. Firmware that a vendor rebuilds from source will not match byte for byte; the
  downstream-fork case study shows what is left then.
- **The sibling snapshot is close to a copy of the tested image for most benchmark devices** (the same
  regular-file paths and contents for 8 of 11), because devices of one OpenWrt target share nearly all
  packages. It is always a different official file, and in
  an audit of vendor firmware it is the right reference, but for this benchmark the "no sibling snapshot"
  column is the conservative one.
- **Seeded errors are not field data.** See [docs/LIMITATIONS.md](docs/LIMITATIONS.md).

## How it relates to other tools

- **BomTrace** (`ssophiz/bomtrace-iot-bom-verifier`, also written for this hackathon) reconciles OpenWrt's
  published BOMs with the opkg or apk database and is careful about its scope: its README states that the
  database is not independently authenticated and that a one-byte change to BusyBox produces no finding.
  BOMwitness starts from that gap. BomTrace also supports apk-based 25.12 images, and its experimental second
  mode checks BOMs that carry per-file paths and SHA-256 values, X.509 certificate fields, a TensorFlow Lite
  header and explicit certificate and model configuration references. BOMwitness has none of that. The
  second mode needs hashes in the declaration, which OpenWrt's published BOMs and the benchmark BOMs do not
  carry, so only the database mode is compared here.
- **Syft** and **cve-bin-tool** are generators and scanners, not verifiers. They appear as baselines only
  through small diff scripts of ours (`bench/baselines.py`).
- **JBomAudit** (NDSS 2025), the example tool in the SafeIoT supply-chain pipeline, checks Java SBOMs
  against JAR contents. BOMwitness applies the same idea, verify the BOM against the artifact and not
  against metadata, to firmware.
- **EMBA** is a firmware analyser that assembles an SBOM from several detection channels, package metadata
  among them. It was not evaluated here.
- Checking an artifact against a BOM is not new in itself: JBomAudit does it for JARs, BomTrace's second
  mode for hash-carrying BOMs, and Belcarra's SBOM Artifact Verifier for signed packages whose SBOM lists
  file hashes. What BOMwitness adds is narrower: a package reference authenticated separately from the
  device and the BOM, applied to hashless package-level declarations, with measurements of how that
  reference ages.
- Commercial binary analysis products advertise SBOM validation against firmware. They are closed, so
  nothing here is compared with them.

## Scope

In: OpenWrt opkg releases (tested on 23.05 and 24.10, seven package architectures), SBOM and CBOM
verification, cross-BOM consistency, a model-file presence check (file header, for some formats header plus
file extension; no check of weights, licences or the runtime a model needs). Out: executing firmware, encrypted
images, apk-based releases, vulnerability matching, and any claim about firmware families that were not
measured. The AI-BOM part is a presence check exercised only by synthetic fixtures (unit tests and
[examples/aibom/](examples/aibom/)), because the evaluated router images contain no models.
