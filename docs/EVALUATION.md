# Evaluation

Every number quoted in this repository comes from a file under `results/r2/`. The tables in
`results/r2/SUMMARY.md` are generated by `bench/summarize.py` from the per-image case files.

## Data

Fourteen official OpenWrt release images (`bench/images.json`): seven from 24.10.8 and seven from 23.05.6,
across seven package architectures (MIPS big-endian and little-endian, AArch64 Cortex-A53 and Cortex-A72,
ARMv7 Cortex-A7 and Cortex-A9, x86-64). Each image is downloaded from downloads.openwrt.org and checked
against `profiles.json`, which the usign-signed `sha256sums` of its target pins. URLs, hashes and the
signing key are recorded in `bench/images.lock.json`. Nothing from OpenWrt is redistributed.

## Tuning and held-out images

- **Tuning (4 images):** three 24.10.8 images used in an early feasibility spike and one 23.05.6 image. The rules,
  the reference handling and the scoring were written and debugged on these.
- **Held-out (10 images):** downloaded and unpacked early so that the reference indexes could be built in
  one go, but not verified or benchmarked until the rules were frozen. The freeze is commit `0f83a98`
  (tag `rules-frozen-r2a`) of the development history; see `docs/PROVENANCE.md`. `results/r2/RUN.json` records the commit the full run was started from.

Anything changed after the freeze is listed under "Changes after the freeze" below, with its effect.

## Ground truth and seeded errors

The correct BOM for an image is its package list (name and version of every installed package, read from the
image's own database, which we take as correct for an unmodified official image whose hash is in the image
list that the signed checksum file pins). Each case applies one
mutation and has one label, `(class, component)`.

| Class | What changes | Label |
|---|---|---|
| M1 omitted | one component is removed from the BOM | undeclared_component |
| M2 other-release version | the BOM carries the version the other release series ships (stale on 24.10 images, optimistic on 23.05 images) | wrong_version |
| M2b fabricated version | the last number of the version is raised by one | wrong_version |
| M3 phantom | the BOM lists a package that is not in the firmware | absent |
| M4 implant | a real package's files are written into the firmware; BOM and database say nothing | undeclared_component |
| M4u implant, unindexed feed | the same, with a package from the large `packages` feed that the path index does not cover | undeclared_component |
| M5 swapped binary | a component's executable is replaced by the other release's build; BOM and database unchanged | wrong_version |
| M6 patched binary | one byte of a component's executable is flipped; BOM and database unchanged | bytes_differ |

Twelve targets per class per image (six for M4u), chosen by a seeded random generator
(`random.Random("20261127:<image>:<class>")`).

For M1 to M3 the device's own database is put in three states:

- **honest**: untouched, so it still tells the truth;
- **colluding**: edited to agree with the wrong BOM;
- **stripped**: deleted.

M4 to M6 are **unaware**: the firmware changed and neither BOM nor database mentions it.

## Tools compared

- **BOMwitness**, default configuration: byte hashes, version markers, the release manifest (pinned by the signed checksum file), one sibling
  snapshot where the target has another device, file-path index.
- **BOMwitness ablations**: without the sibling snapshot; feeds only (no manifest, no snapshot); grade A
  only; grade B only; without timestamp normalisation; and with the device database's disagreements counted
  as findings (to show what grade C adds when the database happens to be honest).
- **BomTrace** (`ssophiz/bomtrace-iot-bom-verifier`, commit `64e5264`): its published
  `verify_openwrt_bom.py`, unmodified, through its own command line. Our adapter writes the declared BOM as
  CycloneDX 1.4 and a tar archive holding the tree's package database, and maps its three rule ids to our
  classes. BomTrace is designed for published BOMs and an intact database and says so. When the archive
  holds no database its verifier exits with an error and no result; the tables show that as "unsupported
  input, 0 labels returned", not as a run that found nothing. Its experimental second mode (`bomtrace.py`)
  checks BOMs that carry per-file paths and hashes, certificate fields, a TensorFlow Lite header and
  configuration references; the BOMs in this benchmark, like OpenWrt's published ones, carry names and
  versions only, so that mode has no input here.
- **Syft-diff**: Syft 1.57.2 inventories the tree; our script compares that inventory with the declared BOM
  by name and version. Syft is an SBOM generator. The diff is ours.
- **cve-bin-tool-diff**: cve-bin-tool 3.4's version scanner (signature checkers over file contents, no CVE
  database) identifies products; our script compares them with the declared BOM. The diff and the product
  to package name table are ours.

## Scoring

Per tool and database condition:

- **recall** = labelled errors found / labelled errors. For `undeclared_component` the package must be named.
- **clean false alarms** = the tool's findings on the unmodified image with the correct BOM.
- **precision** = TP / (TP + case FP + clean FP). Case FP are findings a mutation caused beyond its label.
  Clean FP are counted once per image for that database condition.
- **attributable precision** = TP / (TP + case FP), which sets the clean-control findings aside. For the
  baselines the clean findings are mostly naming differences in our diff scripts, so both are shown.

One scoring decision deserves a note. When an implanted file is flagged as unaccounted executable code but
the package is not named, the case counts as a miss (recall stays strict) and the file-level finding is not
counted as a false positive, because the file really was implanted.

In the stripped condition the Syft-based diff reports every declared component as absent. A phantom
component is among them, so that tool is credited with the phantom cases there; its precision in that
condition shows what the credit is worth.

For BOMwitness the honest, colluding and stripped rows are identical by construction, because it never
reads the database. The benchmark still runs all three trees and compares, and a unit test asserts it.

## Other measurements

- `results/r2/cbom/`: seeded CBOM and cross-BOM errors (15 classes) on every image.
- `results/r2/drift.json`: the same device across 15 point releases, verified against today's feeds.
- `results/r2/official-bom.json`: OpenWrt's published per-target BOM verified against each device image.
- `results/r2/inventory.json`: component list derived from bytes alone, compared with the package list.
- `results/r2/sibling-overlap.json`: how much each sibling snapshot overlaps the image it helps verify.
- `results/r2/far-sibling/` and `results/r2/wide-index/`: the benchmark rerun with the least similar sibling,
  and with the large feeds indexed as well (BOMwitness only).
- `results/r2/case-study-immortalwrt.json`: an unmodified image of a downstream fork, checked against
  upstream OpenWrt and against the fork's own signed download tree.

## Reproducing

```sh
python -m venv .venv && .venv/bin/pip install -e ".[test]"
.venv/bin/python bench/prepare.py                      # images and sibling snapshots (about 190 MB)
.venv/bin/python scripts/build_reference.py $(.venv/bin/python -c "import json;print(' '.join(sorted({i['release']+':'+i['target'] for i in json.load(open('bench/images.json'))['images']})))")
cd bench
for id in $(../.venv/bin/python -c "import json;print(' '.join(i['id'] for i in json.load(open('images.json'))['images']))"); do
  ../.venv/bin/python run_cases.py $id; ../.venv/bin/python run_cbom.py $id
done
../.venv/bin/python summarize.py ../results/r2/cases ../results/r2
../.venv/bin/python drift.py; ../.venv/bin/python official_bom.py; ../.venv/bin/python inventory_eval.py
../.venv/bin/python sibling_overlap.py; ../.venv/bin/python case_study.py
```

The baselines need Syft 1.57.2 at `tools/syft/syft`, cve-bin-tool 3.4 in `work/baselines/cvebin-venv` and a
clone of BomTrace at `work/baselines/bomtrace` (commit above). `--no-baselines` skips them. The reference
index downloads about 2.5 GB in total and keeps only per-file hash manifests.

The shared OpenWrt feeds change over time. A rerun months later will see more drift than the committed
results; the frozen feeds, the manifests and the images do not change.

## What the freeze covers, and changes after it

The freeze applies to the **primary evaluation**: the held-out table, the per-class table and the clean
controls, produced by the one full run that `results/r2/RUN.json` records (commit `0f83a98`, clean working
tree). The ablation columns come from that same run. Everything else (drift, published BOMs, inventory,
sibling overlap, far sibling, wide index, the fork case study, the CBOM benchmark's summary, the timing
measurement and the review analysis) was scripted and run after the freeze, and for those the freeze is not
a claim.

The history is public, so `git diff rules-frozen-r2a -- bomwitness bench/run_cases.py bench/baselines.py
bench/summarize.py` shows every later change to the rule and scoring files. In words:

1. **`bomwitness/verify.py`, one commit, two edits.** (a) The text of one `wrong_version` message when the
   sibling image and the feed index give the same label. (b) Candidate attribution for files that no
   declared component explains: candidates found through the feed are now merged with what a sibling
   snapshot already attributed to the same package, instead of being skipped. The fault showed up in the
   pipeline example, which runs without a file-path index, where a configuration file could be attributed
   to a second package shipping identical defaults. Regression test:
   `test_snapshot_and_feed_attribution_are_merged_without_a_path_index`. An earlier version of this
   document said the benchmark does not take that code path. That was too strong: the merged function is
   also called when a path index is present. What can be said is narrower and is the evidence below: the
   frozen run stands as recorded, and a rerun of three images after the change reproduced it exactly.
2. Wording of one report message, a `--name` option for the report title, and an environment variable in
   `bench/run_cases.py` that selects another snapshot directory (for the far-sibling check).
3. New measurement scripts that only consume the verifier: drift, official BOM, inventory, sibling overlap,
   far sibling, case study, error analysis, headline.

4. Later, after all results were produced: the command line entry point silences one third-party deprecation
   warning (`cryptography` warns about CA certificates with a non-positive serial number; they are still parsed
   and reported). `bomwitness/verify.py`, `crypto.py` and `reference.py` are unchanged since the commit that
   produced the post-freeze check, and the benchmark does not go through the command line entry point. The
   pipeline harness, which compares the example run with its expected findings, still ends with `PASS`.

5. After an independent review: the command line looks a sibling image up in the image list (`profiles.json`,
   pinned by hash in the signed checksum file) and the report states how far each reference input was
   authenticated; report wording for grade A and for model detection was narrowed; `bench/review_r3.py` and
   `bench/timing_e2e.py` were added. None of these touches `verify.py`, `crypto.py`, `reference.py` or the
   benchmark scripts. See `docs/REVIEW-RESPONSE.md`.

6. After a second independent review: **`bomwitness/verify.py`, wording and one pass-through field, no
   rule.** (a) Reason and detail strings were rewritten so that a grade A match is described by what was
   compared, with counts (files present, matched, matched only after date strings were masked,
   configuration files not compared, files missing), and no longer as "every file byte-identical".
   (b) A snapshot now carries a trust field (`authenticated`, `unlisted`, `supplied`) that the caller sets
   and that selects the words a reason uses for the snapshot; no branch that picks a verdict reads it.
   (c) The report's `options` block lists that field, and an `undeclared_component` detail says how many
   of the attributed files have the reference hash. `report.py` and `cli.py` changed with it (wording, the
   trust lines in the compact output). `bench/run_cases.py`, `baselines.py` and `summarize.py` are
   unchanged since the earlier rerun.

7. After a third independent review: **`bomwitness/verify.py`, what a finding reports, no rule.** (a) The
   attribution of files that no declared component accounts for now keeps, per file, which input matched
   it (the feed, or which snapshot). The candidate sets, the ranking and the grouping are the same code as
   before; only the detail text and a new `evidence` field are built from the added bookkeeping. A file
   that only a snapshot matched is reported with the snapshot's name, trust status and version of the
   package, where the text used to give the feed's current label. (b) Verdicts that rest on a snapshot or
   on another release carry an `evidence` field, the stale note names that input, and a snapshot's name
   follows its trust words in square brackets. (c) The other-release reason gives counts (differing files
   that match that release's build, files that match neither, files that match this release) in place of
   "a file that differs ...". (d) A grade A reason with zero matched files says that no file was positively
   matched. `cli.py` lists each `--alt-release` with its signing key in the trust block; `report.py`
   describes grade A as "no compared file differs". `bench/run_cases.py`, `baselines.py` and
   `summarize.py` are unchanged.

8. After a fourth independent review: **`bomwitness/verify.py`, what one finding reports, no rule.** (a) When
   the files present match this release's reference build of another version and another release's build of
   the declared version has different bytes, the `wrong_version` reason used to say only "another release".
   It now names that release, the key that signed its checksum file, the version it records and how many
   files were compared, and the verdict carries an `evidence` field like the other other-release verdicts.
   `alt_lookup` keeps the first such release for that text; whether the branch is taken is decided exactly
   as before. (b) The other-release grade A reason separates files that have this release's reference
   SHA-256 from files that match it only after build-date strings are masked. (c) The module docstring and
   the report's grade A paragraph say that identical configuration files count and differing ones are
   skipped in the comparison with this release's package, that a snapshot's record leaves configuration
   and account files out, and that snapshot and other-release comparisons use the raw SHA-256.
   `bench/run_cases.py`, `baselines.py` and `summarize.py` are unchanged.

The evidence that items 1 and 2 are result-neutral: three images (two held-out, one tuning) were rerun with
all baselines after those changes: 558 rows, identical labels and scores for every tool, identical
clean-control findings (`results/r2/postfreeze-check/COMPARISON.json`). Eight of the ten held-out images
were not part of that rerun, so for them that claim rested on the frozen run itself.

The evidence that item 6 changed no verdict: all fourteen images, the ten held-out ones included, were
rerun through `bench/run_cases.py` (BOMwitness and its ablations; the baselines do not use the changed
code and were not rerun) and compared field by field with the committed case files by
`bench/verdict_check.py`. Compared: every case's label, every configuration's hit, false-positive count
and extra findings, the verdict for the seeded target, and on the clean controls the hard findings, the
verdict counts per configuration, the label sources and the list of components that did not verify. Not
compared, because they are expected to differ: the reason text, timings, and the baselines' columns. The
result is in `results/r2/r4-verdict-check/COMPARISON.json`, with the differences found (none) and the
number of reason strings whose text changed. The same script was first run with the unchanged code of the
previous commit, to show that the rerun itself reproduces the committed files on this machine and date.
The snapshot files used are byte-identical to those of the frozen run (their SHA-256 values are in the
comparison file).

The evidence that item 7 changed no verdict is the same procedure, repeated: all fourteen images rerun
with the previous head's code and with the changed code, both compared with the committed case files.
Result: `results/r2/r5-verdict-check/COMPARISON.json`. A unit test fails if `verify.py`, `reference.py` or
`bench/run_cases.py` differ from the files that rerun used. What this does and does not show is unchanged:
it covers the recorded labels, scores, seeded-target verdicts and clean-control findings of every
configuration, not every per-component verdict under every ablation.

Because of that gap a second, wider comparison was added for item 7. `bench/full_digest.py` runs the old
code and the new code side by side on all fourteen images, in each of the six configurations and for
three declarations (the correct BOM, the BOM with its first twenty components omitted, the BOM with every
version changed), and compares every component's verdict, grade, actual version, actual component, label
source and file counts, and every finding's class, component, grade, files and alternatives. Reason and
detail text is left out, because it is what changed. Result: 252 runs, 35,814 component records, 13,365
findings, no difference (`results/r2/r5-verdict-check/FULL-DIGEST.json`). The three declarations are not
benchmark cases and nothing is scored on them; they make the verifier take its attribution and
wrong-label branches on real images.

Item 8 was checked the same way, both checks repeated: `bench/verdict_check.py` on reruns of all fourteen
images with the previous head's code and with the changed code (0 differences each), and
`bench/full_digest.py`, previous head against changed code (252 runs, 35,814 component records, 13,365
findings, no difference; the two digest files are byte-identical). Results:
`results/r2/r6-verdict-check/COMPARISON.json` and `FULL-DIGEST.json`. The unit test that guards the rule
files now points at these files.

## Counting, variability and candidate pools

`results/r2/review-r3.json` (from `bench/review_r3.py`, a post-freeze analysis of the committed case files
that reruns nothing) records:

- **Distinct errors.** A BOM-level error (M1 to M3) is one (image, class, component) scored under three
  database states; an unaware error (M4 to M6) is scored once. Held-out: 480 + 420 = 900 distinct errors in
  1860 rows. Tuning: 360 in 744.
- **Variability.** Errors on one image share its packages and its reference, so they are not independent,
  and the Wilson intervals quoted in the headline only describe these cases. The file gives recall per
  held-out image for the three BOMwitness configurations, with minimum, median and maximum.
- **Baselines without a database.** For each condition, how many rows BomTrace's verifier produced a result
  for (0 of 480 when the database is stripped: unsupported input) and which rows the Syft-based diff was
  credited with (the 120 phantom rows).

**Candidate pools.** Seeded targets are sampled, per image, from packages the reference can speak about:
M1 and M2b from installed packages that have a reference entry and at least one file in the image; M2 and
M5 from those whose version differs between the two release series; M3 and M4 from base-feed packages that
are not installed (up to 4 MB, no kernel modules or translations); M4u from the `packages` feed; M6 from
components that verified at grade A on the clean image and ship an executable. Components without a
reference package are therefore never targets; on clean images they end as `unverifiable`. Images of the
same target also share most packages, so targets repeat across images of one family.

## Timing

`seconds_median` in the case files is the median duration of one in-process `verify()` call per case, with
the root filesystem already unpacked and hashed and the reference cache warm. BomTrace and Syft were timed as
separate command-line processes (and BomTrace's stripped runs exit immediately). These figures are not
comparable with each other. `bench/timing_e2e.py` measures what a user waits for, the command line from
image to report: `results/r2/timing-e2e.json` (one machine, the repository example, measured after the
freeze).

## What the results show, and what they do not

All numbers are in `results/r2/HEADLINE.md` (also in the README) and `results/r2/SUMMARY.md`. Every miss is
listed in `results/r2/ERROR-ANALYSIS.md`.

- **Database dependence.** With an honest database, BomTrace and the Syft-based diff find every BOM-level
  error and BOMwitness misses a few. With a colluding database both run and return no label. With a missing
  database BomTrace's verifier cannot run (unsupported input, 0 labels returned), and the Syft-based diff
  reports every declared component as absent, which credits it with the 120 phantom rows of 480 at a
  precision of 0.055. This is the designed behaviour of the database-reading modes of those tools, shown
  here so the dependence is measured and not just asserted. It says nothing about tools that were not run.
- **Where BOMwitness misses.** (a) An implanted package from the unindexed `packages` feed is always flagged
  as unaccounted executable code but is named only about two times in three. (b) Three phantom packages
  (hostapd and wpa_supplicant variants) were accepted: the firmware contains one of their two files, a
  script that the installed `wpad` package ships with identical bytes, while their executable path is a
  symlink to the multi-call `wpad` binary. The rule verifies the files that are present and does not require
  every file of a package. Requiring a package's executables to be present would catch these; that rule was
  not changed after the freeze. (c) A fabricated version on
  a component that no manifest, frozen feed or sibling pins; in one case a coincidental version string in
  the binary even "confirmed" the fabricated version at grade B, which is a reminder that a marker is
  weaker evidence than a hash.
- **False alarms.** All clean-image false alarms on the held-out set are the same package (`e2fsprogs`) on
  targets with a single device and therefore no sibling snapshot: the image's build of it differs from the
  shared feed's build under the same label. The tool says `bytes_differ`, which is true, and cannot say
  which build is the odd one.
- **Sibling snapshots.** Devices of one target share nearly all packages. For most benchmark images the
  most similar sibling has the same regular-file paths and contents (`bench/sibling_overlap.py` does not
  compare symlinks, file metadata or the SquashFS container), and even the least similar one shares 80 to 100
  percent of the tested image's packages (`bench/far-siblings.lock.json`). The snapshot is therefore best read as "the
  publisher's frozen release root filesystem for this target", not as an independent witness. The
  no-snapshot and feeds-only columns show what remains without it.
- **Drift.** The older the image, the less of it today's shared feed can confirm at grade A, and the
  more false alarms the feed alone produces. The release manifest recovers labels, and the snapshot recovers
  bytes.
- **Published BOMs.** Of 1868 claims, 1674 verify at grade A and 31 at grade B, 122 are unverifiable, 34
  are `wrong_version`, 4 are `bytes_differ` (`e2fsprogs` and `ucode-mod-fs`) and 3 are absent from the
  device image. The 34 are a disagreement about label granularity, not about code: the BOMs list
  out-of-tree kernel-module packages (mac80211 backports, mt76, ath10k-ct) with the kernel version only,
  while the frozen feed labels the same bytes with the kernel and the driver version. The BOMs also do not
  list device-specific packages. `bench/official_bom.py` runs BOMwitness only; it uses the device database
  just to confirm that packages beyond the BOM are installed. No database-reading verifier was run on
  these BOMs, so nothing here says what one would report. We
  have not found a statement that the per-target BOM is meant to describe each device image, so this is a
  coverage observation.
- **A second publisher and a fork.** The ImmortalWrt image verifies against its own signed download tree
  with a different key and no code change. Checked against upstream OpenWrt, fewer than half of its
  components verify at grade A, which is the honest picture for rebuilt firmware: grade A evidence needs
  the builder's own packages or manifests.
- **Not shown.** Nothing here measures real-world BOM error rates, vendor firmware rebuilt with a private
  toolchain, encrypted images, or statically linked code inside other binaries.
