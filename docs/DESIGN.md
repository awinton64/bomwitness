# Design

## The problem

A manufacturer, auditor, regulator or buyer receives an SBOM (sometimes with a CBOM) for a device's firmware
and has to decide whether to believe it. The open tools evaluated here (BomTrace's database mode and a diff
built on Syft's inventory) get their package inventory from the database inside the firmware
(`/usr/lib/opkg/status` on OpenWrt). A verifier
built on that inventory answers one question: does the BOM agree with what the firmware says about itself?

That fails in three situations. How common each is in shipped vendor firmware was not measured here.

| Device database | What a database-reading verifier can do |
|---|---|
| Honest | Everything. It finds every BOM error. |
| Colluding: edited, or generated by the same faulty process, so it agrees with the wrong BOM | Nothing. BOM and database agree. |
| Stripped: removed from the image (OpenWrt's build system has an option for this) | It has no usable input, or it reports every declared component as missing. |

And in every case a file that changed under an unchanged label (a swapped or patched binary) is invisible,
because no label changed.

## Threat model

The BOM under test and the device's own package database are untrusted. Both may be wrong by accident
(stale, generated from the wrong build) or on purpose. The firmware bytes are what they are. The trusted
side is the publisher's release material, taken over the network and authenticated with two pinned OpenWrt
usign keys: a signed checksum file per target, package indexes that are signed or pinned by that checksum
file, the release manifest (pinned by the checksum file) and other official images of the same release
(their hashes are in `profiles.json`, which the checksum file pins). Packages are pinned by index hashes
and files by per-package SHA-256 manifests. So every file hash is reached through a signed chain; files and
packages are not signed individually.

What the tool does not authenticate, and therefore assumes:

- A snapshot JSON file passed with `--snapshot` is a local input and is used as supplied.
- A sibling image passed with `--sibling-image` is looked up by SHA-256 in `profiles.json`, the image list.
  The signature is on `sha256sums`; `profiles.json` is checked by its hash in that file and has no
  signature of its own. The command's output and the report say whether the image was found; an unlisted
  image is still used, with a warning. The benchmark fetches its siblings itself and always checks them
  against `profiles.json` (`bench/prepare.py`).
- The result of that lookup travels with the snapshot into the verifier as a trust flag (`authenticated`,
  `unlisted` or `supplied`; a snapshot file is always `supplied`, whatever it says about itself). The flag
  never changes a verdict. It changes the words: a reason that rests on an unauthenticated snapshot says
  "the supplied snapshot (not authenticated by this run)" or "the supplied sibling image (not
  authenticated ...)", and no reason calls such a source official. The benchmark passes snapshot files, so
  its recorded reasons use the "supplied" wording even though `bench/prepare.py` checked every sibling.
- Which input supported a finding is part of the finding. A verdict or finding that rests on a snapshot or
  a sibling image gives the trust words above followed by the input's name in square brackets, and the
  version that input records. One that rests on another release (`--alt-release`) names the release; that
  reference is authenticated like the primary one and the compact output names the key that signed its
  checksum file. The JSON report carries the same facts in an `evidence` field (input, trust, version,
  number of files). For an `undeclared_component` the source is kept per file: a file that only a snapshot
  matched is reported with the snapshot's version of the package, a file that the feed matched with the
  feed's, and if the feed's current build matched none of them the finding says so. The stale note
  ("firmware has X; the reference feed now ships Y") says which input X was verified against when that
  was a snapshot or another release.
- The reference cache is verified when an item is first fetched and trusted afterwards. Anyone who can
  write to the cache directory can change verdicts.

Out of scope: an attacker who controls the publisher's signing key or build system; firmware that is
encrypted or not a SquashFS root filesystem; code outside the root filesystem (boot loader, kernel image);
run-time behaviour.

## Evidence grades

| Grade | Evidence | Role |
|---|---|---|
| A | No compared file of the package differs from the reference. The package's files that are present in the image are compared by SHA-256 with the files in the publisher's package (index authenticated as above, then per-file SHA-256), or with the hashes recorded for that package in a sibling snapshot. Configuration files (`conffiles`) and `etc/passwd`, `etc/group`, `etc/shadow` count as matches when they are identical and are skipped when they differ. Accepted as a match: a file that differs from the reference only inside embedded date and time strings, which are masked before comparison. Not required: that every file of the package is present, or that any file matches. A package whose only file in the image is a changed configuration file passes with zero matched files, and its reason says that no file was positively matched. So grade A means that nothing compared contradicts the claim, not byte identity of the whole package; the reason text of each grade A verdict gives the counts. The label for those bytes comes from the feed index, the release manifest, or a sibling image (authenticated or supplied, as stated in the reason). | Decides verdicts |
| B | Intrinsic to the bytes: the version marker that the reference build of the same component carries, versioned file names, SONAMEs, algorithm names | Decides verdicts when A is not available; always labelled B |
| C | The device's own package database | Shown in its own report section, never decides a verdict |

## Reference sources and why there are four

1. **Frozen feeds.** `targets/<target>/packages` and `targets/<target>/kmods/<kernel>` belong to one point
   release. Their indexes are listed in that release's signed `sha256sums`, so the tool treats a label there
   as exact. This rests on OpenWrt not republishing a point release's target directory; the tool pins what
   the signed checksum file says and does not check that assumption over time.
2. **Shared feeds.** `packages/<arch>/{base,luci,packages,routing,telephony}` are one directory for every
   point release of a series. They are rebuilt and relabelled after the release. Identical bytes can carry
   a newer label, a package can move to a new upstream version, and a rebuild can change bytes (BusyBox
   embeds its build time). So "same bytes, different label" cannot be called an error from this source alone.
3. **Release manifest.** The per-target manifest, pinned by hash in the signed checksum file, lists the
   version of every default package at release time. It gives labels that the shared feed has since changed.
4. **Sibling snapshot.** Another official image of the same release and target still carries the bytes the
   release was built from. Its file hashes and package lists restore grade A evidence for components whose
   feed copy has moved on. When the image's SHA-256 is in the image list that the signed checksum file
   pins, its package lists are the publisher's statement inside a hash-pinned artifact, not the device
   under test describing itself. An image that is not listed, or a snapshot file, is evidence only as far
   as the person who supplied it is trusted, and the report says which case applies.

`bench/drift.py` measures how much each source contributes as an image ages.

## Verdict rules

For a declared component (name, version), after the name is matched to a reference package (exact name,
ABI suffix such as `libubox` for `libubox20240329`, `Provides`, or source package name):

| Situation | Verdict |
|---|---|
| No file of the reference package is in the firmware | `absent` |
| Every file that is present and compared matches (see grade A above for what is not compared and what is masked) and the declared version equals the feed label, the manifest label or the sibling image's label (a version without OpenWrt's `-rN` release suffix is accepted at upstream granularity) | `verified_A` |
| Every compared file matches, the label differs, and the feed is frozen, or the manifest or the sibling image names another version, or the publisher's build of the declared version in another release has different bytes | `wrong_version` (A) |
| Every compared file matches, the label differs, and nothing pins the label | `label_unconfirmed` (review) |
| Bytes differ from the feed copy but equal the sibling image's build | `verified_A` or `wrong_version`, by that build's label |
| Bytes differ only inside embedded date and time strings | treated as a match; the reason text counts such files |
| Every file present at the component's paths has the SHA-256 of another declared component's file | `absent` |
| The differing files have the SHA-256 of another reference package's files | `wrong_component` |
| A differing file has the SHA-256 of the same package's build in another release (`--alt-release`). One such file is enough; the reason counts the differing files that match that build, those that match neither build, and the files that match this release | `verified_A` or `wrong_version`, by that build's label |
| Same label as the reference, different bytes, reference build carries a version marker the firmware files lack | `wrong_version` (B) |
| Same label as the reference (or as the sibling image), different bytes | `bytes_differ` (review) |
| Feed moved to another version, firmware files carry the declared version marker | `verified_B` |
| Feed moved, reference build carries a marker, firmware files do not carry the declared one | `wrong_version` (B) |
| Feed moved, no marker anywhere | `unverifiable` |
| The package ships no files (a metadata package) or no reference package has this name | `unverifiable` |

Image level: every regular file not accounted for by a declared component is attributed through the
file-path index (or the sibling snapshot, or, for unindexed feeds, by fetching packages with similar
names). A match is an `undeclared_component`; an executable that nothing explains is an `undeclared_file`.

## CBOM and cross-BOM rules

Certificates and keys are found by parsing, algorithms by name inside the bytes of each component's files
(grade B, see `bomwitness/crypto.py` for the pattern table). These checks compare what is in the image with
what the CBOM declares. No signed reference is involved, except indirectly through the provider rule, which
accepts a provider that the SBOM check verified at grade A or grade B. Declared CBOM entries are checked:

- a declared certificate is matched to one in the image by SHA-256 fingerprint (or by subject when the
  declaration has no fingerprint and the subject is unique) and then compared field by field: key
  algorithm and size, signature hash, expiry. A certificate found in the image must be declared;
- a standalone key is reconciled by fingerprint only: a declared fingerprint must be in the image and a key
  in the image must be declared. No further field of a key is compared;
- a declared algorithm must name a providing component; that component must be in the SBOM
  (`provider_not_in_sbom`), its bytes must have verified (`provider_unverified`), and one of its files must
  carry the algorithm's name (`algorithm_not_evidenced`);
- a component whose files carry algorithm names must have CBOM entries
  (`crypto_component_without_cbom_entry`, `undeclared_algorithm`);
- weak keys, expired certificates, deprecated primitives and private keys shipped in the image are reported
  as policy observations.

## AI-BOM

`bomwitness/aibom.py` recognises model files by file header where the header is distinctive (GGUF,
TensorFlow Lite, HDF5) and by header plus file extension where it is not: a safetensors file starts with a
length and a JSON brace, a PyTorch archive is an ordinary ZIP file, and an ONNX file is a Protocol Buffers
message with no magic number, so for these three the extension carries most of the identification. Files
are matched to declared model components by SHA-256. That is the whole scope: a presence check. It does not
read weights, check a licence, or check that the runtime a model needs is in the SBOM. The router images
used in the evaluation contain no model files, so this part is covered only by synthetic fixtures: unit
tests, `examples/aibom/run.py`, and `examples/aibom/unified.sh`, which adds two placeholder model files to
an official image's root filesystem and runs the SBOM, CBOM and AI-BOM checks in one command. No accuracy
claim is made for it.

## What is automatic, what needs review, what stays unverifiable

- Automatic pass: `verified_A`, `verified_B`.
- Automatic fail: `wrong_version`, `wrong_component`, `absent`, `undeclared_component`, `undeclared_file`.
- Needs a person: `bytes_differ` (rebuild or modification), `label_unconfirmed`.
- Unverifiable: metadata packages, components whose reference has moved and that carry no marker,
  components with no reference package.
